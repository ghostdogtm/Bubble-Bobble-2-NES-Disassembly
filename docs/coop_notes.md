# Simultaneous co-op: lab notebook

Append-only log of verified facts, design decisions and per-phase results for the co-op work
(plan: `tmp/bb2_coop_implementation_plan.md`; perf background: `docs/perf_notes.md`).
Branch: `bb2_coop_implementation`, started from `8c4bb2c` (perf branch merged into main).

## Architecture decisions (orchestrator, 2026-10-05)

These refine or replace parts of the plan. Where they conflict with the plan, this section wins.

### D1. Co-op code lives in the fixed bank E, not in PRG-RAM
- MMC3 is always used in PRG mode 0 (every `$8000` write has bit 6 clear), so `$C000-$DFFF` is
  permanently bank `$0E` and `$E000-$FFFF` is bank `$0F`.
- Bank E (US) carries two unreferenced filler blobs: `fill0E_Engine.bin` (960 B at `$CF40`,
  label `DATA_0ECF40`, no references) and `fill0E_Tracks.bin` (1789 B at `$D903`, after
  `FixedBankTracks`). Both are marked as never accessed in the disassembly's CDL comments.
- So all co-op routines are plain ROM code in bank E (US branch only; JP keeps its filler).
  They are callable from every bank without bank switching. No `CopyCoopEngine`, no
  self-modifying code, no code in WRAM.
- Bank F still has ~238 free bytes for tiny hooks; prefer `JSR CoopXxx` into bank E.
- PRG-RAM (8 KB at `$6000-$7FFF`, NES 2.0 header, `$A001 = $80`) is still added, but for
  **data only** (shadow context, flags).

### D2. One "P2 window" per tick instead of per-routine two-pass wrappers
The plan wraps each player-related routine (player update, HandleShooting, enemy collision,
bubble touch, projectile collision) in its own swap pair. That costs ~10 swaps per tick.
Instead, P1 stays resident for the whole original tick, and **one swap window** per tick runs all
of P2's work:

```
every tick : [CODE_078247 if ram_04D1]  P1 player update
odd tick   : BubblesTravelUpdate  HandleShooting(P1)
             >>> P2 WINDOW: swap in P2 / P2 player update / HandleShooting(P2) /
                 P2's own emerging bubble update / P2 bubble-touch loop / swap back <<<
             UpdateBubbles (P1 touch inside; skips P2's emerging bubble)  AnimateObjects
even tick  : PlayerCheckEnemyCollision(P1)  enemy AI  CODE_0FFD89  UpdateProjectiles  CODE_078916
             >>> P2 WINDOW: swap in P2 / P2 player update / PlayerCheckEnemyCollision(P2) /
                 (projectile check, see Phase 5) / swap back <<<
             AnimateNonBubbles
then       : DrawObjects ... (P1 resident, P2 in OSLOT_P2)
```
Order changes inside a tick are acceptable in co-op mode (coopMode=0 keeps the original order
byte for byte). Benefits: 2 swaps per tick, enemy AI and DrawObjects always see P1 in slot 0 and
P2 in slot 39.

### D3. Swap mechanism
- One shadow block `ctxOther` in WRAM holds the *non-resident* player's context. A swap
  exchanges every native byte of the context list with its shadow byte, and exchanges the
  per-object arrays between slot 0 and `OSLOT_P2` (= 39). `coopResident` (0/1) records who is
  resident; `currentPlayer` is set to the resident player's id.
- The swap is unrolled code generated by a ca65 macro from one address list (adding a missed
  variable is a one-line change). ~16 cycles per byte.
- Per-object arrays (all 12, see `src/ram.inc`): objState, objY, objX, objImgOfs, objImgOfsHI,
  objChrSlot, objChrBank, objAnim, objAnimTimer, objAnimProgress, objAttr, objAnimHI.

### D4. Animation cadence needs no change
`AnimateObjects` (odd ticks) animates slots 20-39 and `AnimateNonBubbles` (even ticks) slots
0-19. P1 (slot 0) and P2 (slot 39) are therefore both animated every 2nd tick, one tick apart.
Keep the `CPX #40` bound in `AnimateObjects`.

### D5. P2's emerging bubble is owned by the P2 window
`BubbleEmergingUpdate` reads the global `shootDir` and its conversion epilogue clears
`shooting/shootSlot/shootQueuedBubbles` and runs `SpawnExtraBubbles` from `shootSlot`. Instead of
a direction resolver, the P2 window calls the emerging update for P2's bubble itself (P2 resident,
so all globals are P2's), and `UpdateBubbles` skips that slot while P1 is resident. Verify the
calling convention of the emerging handler before relying on this.

### D6. Enabling co-op before the menu exists
- `coopMode` lives in WRAM and is cleared by the reset hook.
- Build-time switch: `perf.py build NAME --define COOP_FORCE` makes the reset hook set
  `coopMode = 1` (for manual Mesen testing).
- Harness: co-op scenarios poke `coopMode` (address from the build's labels) early in the run.

## Phase 2 (data model, CoopSwap)

### Implemented
- `src/coop/coop.inc`: the swap list as two ca65 macros, the single source of truth: `COOP_CTX_SCALARS M` (31 entries, one
  per line) and `COOP_CTX_ARRAYS M` (12 per-object arrays), plus `COOP_POWERUP_MASK = POWERUP_CANDY | POWERUP_SHOE`.
  Adding a per-player variable later = add one `M name` line to `COOP_CTX_SCALARS`; both the shadow storage and the
  exchange code follow. (The macro name is passed as a macro parameter: `COOP_CTX_SCALARS COOP_SWAP_SCALAR` works in ca65.)
- `src/coop/coop_ram.asm`: `ctxOther` is now exactly 32 bytes (`$6006-$6025` in c2): one shadow byte per scalar, named
  `ctxOther_<symbol>` (`ctxOther_playerLives`, `ctxOther_playerState`, `ctxOther_shootSlot`, ...) plus `ctxOther_powerUps`
  (only bits 0-1 are ever non-zero). The object arrays need no shadow: slot `OSLOT_P2` (39) is the shadow.
  `coopP2Lives` is a second label on `ctxOther_playerLives` (same address, `$6016`): an equate `coopP2Lives = ...` is
  NOT written to `labels.txt` by `ld65 -Ln`, and the harness looks the symbol up there, so it has to be a label.
- `src/coop/coop_engine.asm`: `CoopSwap` (`COOP_CODE`), generated from the lists. Per scalar
  `LDA native / LDX ctxOther_x / STX native / STA ctxOther_x` (zero-page natives assemble with ZP addressing), per array
  `LDA arr / LDX arr+OSLOT_P2 / STX arr / STA arr+OSLOT_P2`. powerUps (only the 2 per-player bits):
  `x = (powerUps ^ shadow) & mask; powerUps ^= x; shadow ^= x` (keeps the shared bits 2-7 in place, and the shadow never
  gets bits outside the mask). Then `coopResident ^= 1; currentPlayer = coopResident`. Clobbers A and X, preserves Y.
- Test hook (`src/bank_09.asm`, `RoundUpdate`, inside `.ifndef REGION_JP` + `.ifdef COOP_SWAPTEST`): `JSR CoopSwap` /
  `CoopSwapTest_mid:` / `JSR CoopSwap` right after the every-tick player banked sub, before `LDA globalTimer`.
  Normal build: no call to `CoopSwap` anywhere (ROM search for `20 81 CF` finds 0 hits in c2, 2 in c2t).

### CoopSwap size and cycles
- Size 519 bytes (14 ZP scalars x 10 + 17 ABS scalars x 12 + 12 arrays x 12 + powerUps 19 + bookkeeping 11 + RTS 1).
  `COOP_CODE` is now 584 B ($248) of 960 B (376 B free; `CoopReset` is 65 B).
- Cycles: ZP scalar 14, ABS scalar 16, array 16, powerUps 27, bookkeeping 14: body 701 + RTS 6 = **707** after the
  `JSR` has executed, **713** including the JSR. Measured in Mesen: exactly 707 between the first instruction of `CoopSwap`
  and the instruction after its RTS, on every one of 2032 + 3446 + 2052 swaps.
- A co-op tick with one P2 window (2 swaps) pays about 1426 cycles; see item 4 below for the measured self-test cost.

### P2 window (`CoopP2Window`)
1. `bankedSubRetBank` is set to the caller's bank (9, or B for the intro), and `prgBankB` is pushed.
2. `CoopSwap` puts P2 in place (context, slot 0 <-> 39, `currentPlayer` = 1).
3. `CODE_058E83` runs through `RunBankedSub` exactly as `RoundUpdate` runs it, so P2 reads pad 2 through `currentPlayer`.
4. `CoopSwap` puts P1 back.
5. If `prgBankB` changed, `$A000` is mapped back in race-free order (`$8000`=7, `prgBankB`, `$8001`).

With these steps the window leaves the banks unchanged. `$8000` is back to the caller's bank because `RunBankedSub`
restores `bankedSubRetBank`, and `$A000` is back to the caller's bank because of step 5. The intro window also animates
slot 39 on odd ticks (`CoopAnimateP2`), because `AnimateObjects` does not run during the intro. `DrawObjects`, which
comes next there, maps its own bank. `CoopAnimateP2` maps `AnimTable` with the same race-free sequence
`AnimateObjects` uses. That is the Rule 9 order and needs no `nmiProgress` retry, because it is a command-7 switch.

### Spawn and init, and what happens between rounds
- **New game** (`CoopNewGame`, `coopMode` = 1 only): `ctxOther` is zeroed, then P2 gets P1's starting lives (3) and hearts (1).
- **Every round start** (`CoopRoundStartP2`): `CODE_0884CF` runs once per round start, on the tick P1 reaches (X=$1F,
  Y=$C4), because the block then replaces `nmiBankedSub`. Every path into a round goes through it: the normal descent
  `CODE_088342`, the adventure start, the boss-cave fade `CODE_059D9A` (rounds 20/40), and a continue. The hook:
  1. pushes `roundFlags` and `wideScrollDir`;
  2. swaps P2 in and runs P1's own per-life init `CODE_08812A` for P2;
  3. swaps back and restores those two shared bytes (they are the only shared bytes `CODE_08812A` writes);
  4. runs `CoopSpawnP2`. P2 keeps its lives and hearts, because `CODE_08812A` does not touch them.
- **CoopSpawnP2**: Y = P1's Y. X = 256 - P1's X, clamped to [$18,$E8]; P1 always starts at $1F, so P2 always starts at
  $E1 and the clamp never fires. The rest of slot 39 is set up like `CODE_0880C8` sets up slot 0: `objState` 1, anim
  `anPlayerL` (facing left, matching `playerDir` = 1 from `CODE_08812A`), `objChrSlot`/`objAttr`/progress/timer 0,
  `objChrBank`/`objImgOfs` copied from P1, then one animation step for the first frame.
- **Between rounds**: `CODE_0FE36B` deactivates P2. It runs at every round setup (`CODE_088000`), new game, continue,
  ending, title, and bonus-round start. So P2 is not in the descent, the walk-in, the bonus games, or the
  continue/ending screens. The P2 context (lives, hearts) survives in `ctxOther`. Nothing despawns slot 39 between the
  spawn and the next `CODE_0FE36B`: the slot-39 write trace below shows no other writer. Other mass-despawn loops:
  `DespawnNonPlayerObjects` (only from `StartBonusRound`, after `CODE_0FE36B`), `CODE_079BE2` (end of a bonus game),
  `CODE_079F52` (bonus game objAttr). P2 is already inactive at all three.

## Phase 5 (P2 collisions, owner-aware capture)

Build `c5` (commit `c66eb6c`). All hooks are in US-only code (`.ifndef REGION_JP`) and gated by `coopP2Active` or
`coopResident`. New code is in `COOP_CODE2`, which is now $2D3 B (was $139), so 1066 B are free. New `COOP_BSS` bytes:
`coopShotSwapped` and `coopP2SkipSlot`. Bank 9 has 214 B free, bank F 215 B.

### 5.1 Enemy/food collision
- The even window (P2 resident, after P2's player update) calls `JSR PlayerCheckEnemyCollision`, exactly as
  `RoundUpdate` calls it for P1. The routine is in bank F and has no bank or register inputs: it reads slot 0 and
  writes `playerDmgType`, which is P2's byte while P2 is resident. The damage is consumed by P2's next player update,
  in the odd window. For P1 the collision runs before the enemy AI; for P2 it runs after the AI and projectiles. Both
  players consume the damage on the following tick.
- Food: `AddScore` indexes by `currentPlayer`. With `currentPlayer` = 1 it adds to P2's digits `$048A-$0490`
  (`scoreDigitsP2`) and to P2's extra-life accumulator `$049A-$04A0`. Those bytes are unused in 1P; P1's accumulator is
  `ram_0491-$0497`, checked by `CODE_099D3B`. Measured: no `AddScore` with `currentPlayer` = 1 changed a P1 byte, and
  none with `currentPlayer` = 0 changed a P2 byte. The shared bytes touched are `livesCurrentPos` and
  `scoreAdditionDigits`.
- Other effects of the routine: the trash can and the `lastRewardType` / `sameRewardStreak` / `rewardsEaten`
  globals are shared by both players (plan 9.5). The P2 extra-life check and the P2 HUD are Phase 7.

### 5.2 Projectiles: swap only on a P2 hit
The projectile script ops that act on "the player" are:
- `HurtPlayer` and `CatchPlayer` write `playerDmgType`;
- `CopyPlayerState` reads `playerState`;
- `PlayerState` writes `playerState`, `inflateTime`, `extraBubbles`, `ram_0076` and slot 0's animation;
- `Heart` writes `playerHearts` and calls `AddScore`;
- `GetPlayerDist`, `GetPlayerSide` and `HomingPlayer` read slot 0's position;
- the `Jump*` ops read only `scratch4/5` (checked in all scripts in `bank_0A.asm`).

Rewriting all of these ops was not needed:
- After `JSR PlayerCheckProjCollision`, a new gate (`BIT coopP2Active`) calls `CoopProjCheckP2`. If P1 was not hit
  (no `PROJ_HIT`), it runs the same test against slot 39 and `ctxOther_playerInvFrames`. It uses A only and leaves
  the scratch bytes alone.
- On a P2 hit, `CoopProjCheckP2` swaps P2 in (`CoopSwap`, X kept) and sets `PROJ_HIT`. The script then runs unchanged,
  and every op above acts on P2, including `Heart`'s `AddScore` through `currentPlayer` = 1.
- At `@trymove` (the only exit of the op loop), `LDA coopResident / BEQ` calls `CoopProjSwapBack`.
- P1 has priority when both players touch the same projectile.
- The swap pair (~1.4k cycles) runs only on P2 hits: 100 in 34958 ticks.
- Before swapping, `CoopProjCheckP2` also undoes a pending shot exchange (5.4), so `coopShotSwapped` = 0 at every
  `CoopSwap`. Measured: 0 violations.

### 5.3 Bubble touch, hazards
UpdateBubbles' US ladder reaches `CODE_098149` (touch) for states RISING 1, EXPIRING 2, ENEMY 3, ENEMY_EXPIRING 4 and
POWER 5. All other states, including EMERGING and $88/$89, go to `CODE_09815D` or the default `CODE_09813F` without a
touch. `CODE_098149` sets `scratch4/5` = bubble X/Y and X = index, then calls:
- `CODE_098932`, the player part: bounce (`ram_007D` bit 7), push (`bubbleDir` and bit 6), or `PopBubble` with
  `scratch1` = X;
- `CODE_098258`, which is **not** player-related: the bubble's own drift and movement, plus the round-dependent
  despawn.

`CoopP2BubbleTouch` (odd window, after `CoopP2Shoot`, P2 resident) does the following:
- clears P2's `playerHazardTrigger`, `ram_007D` and `playerHazardSlot`, as `UpdateBubbles` does at its start;
- calls `CODE_098932` for every index below `bubbleSlotEnd` whose state is 1-5;
- skips the slot `CoopP2Shoot` updated or converted this tick (`coopP2SkipSlot`), as UpdateBubbles' $80/$88 handlers
  skip the touch;
- does not advance any state machine.

Hazards do not go through `CODE_098149`. Popped special bubbles (state 6, `CODE_098339`: thunder, fire, flood, bomb)
call `HazardCheckPlayer` against slot 0. Its tail now has a gate that jumps to `CoopHazardCheckP2`. That routine tests
the same box (`collW/collH`, `scratch4/5`) against slot 39 and sets `ctxOther_playerHazardTrigger/Slot`. Clear/set
cadence matches P1: the flags set at odd tick N are seen by P2's player updates at N+1 (even) and N+2 (odd), and are
then cleared in N+2's pass.

`ram_051A` is the multi-kill counter. `PopBubble` increments it for every enemy bubble popped, by either player, and
`BubblesTravelUpdate` awards it at the start of the next odd tick in which no chain pops happen. Both players
therefore add to one combined count. The bonus (`AddScore`) is credited to `currentPlayer` = P1 at that point. Nothing
breaks; per-player attribution is logged for Phase 7.

### 5.4 Owner-aware capture
The Phase 4 sketch proposed a P2 test plus owner-aware follow-up code. The follow-up reads are spread over
`CODE_0FFAA3`, `CODE_0FFB0C`, bank B `CODE_0B9630` (which also clears `shootTrigger`), `CODE_0B9AA9` (`$9AC0`,
`shootQueuedBubbles`), bank 8 boss code (`shootQueuedBubbles`) and the `$88/$89` handler `CODE_0FFAB9`. Instead of
editing all of them:
- **Second test.** The exit of `CODE_0FF9E8` (`CODE_0FFA55`, bank F) gets a gate that jumps to `CoopCaptureOther`.
  That routine runs if the enemy is not flagged yet (`ram_00CA` non-zero and bit 7 clear). It applies the same US test
  to the shot in `ctxOther`: the other player must be shooting, the bubble at its `shootInitialSlot` must be $80, and
  the box is `DATA_0FFA56[queued]` plus the enemy W/H. It uses no scratch bytes and keeps X/Y.
- **Exchange on a hit.** It sets bit 7 and exchanges the five shot bytes (`shooting`, `shootInitialSlot`,
  `shootQueuedBubbles`, `shootTrigger`, `shootSlot`) with their `ctxOther` copies (`coopShotSwapped ^= 1`). The
  unchanged follow-up code then traps, bursts or converts the **catcher's** bubble and clears the **catcher's** shot
  state.
- **Restore.** `CoopShotRestore` runs at the start of every P2 window, before `CoopSwap`, and in `CoopP2Deactivate`.
  Between the enemy AI and the even window, nothing reads these bytes (`CODE_0FFD89`, `UpdateProjectiles`, bank 7:
  checked by grep). A later enemy in the same tick again tests the native shot first, then the other one; a hit
  exchanges back.
- **Odd window.** `CoopP2Shoot` dispatches P2's shot bubble by state: $80 goes to `BubbleEmergingUpdate`, $88/$89 to
  `CODE_0FFAB9`, with P2 resident and X = `shootInitialSlot`. P2's $88/$89 bubble is therefore converted before
  `UpdateBubbles`, which never sees it (checker: every `CODE_0FFAB9` call ran on the resident player's own bubble).
- **Timing.** P2's emerging bubble is moved in the odd window, and the enemies test it on the next even tick. That is
  the same as P1, whose bubble is moved in `UpdateBubbles`.

## Phase 6a (enemy targeting)

### Design
- The enemy AI still runs once per even tick with P1 resident. Enemy code reads `targetX`/`targetY` (WRAM, absolute)
  where it read slot 0's `objX`/`objY`; `LDA/CMP/SBC abs` keep their length and cycle count.
- **P2 not in the round** (1P, `coopMode` = 0, between rounds): `CoopTargetTick`, called at the top of the enemy loop
  (`CODE_0B81E3`), sets `coopTarget` = 0 and copies slot 0 into `targetX/targetY` once per even tick, so every
  converted read sees exactly the value it read before. The only enemy-side writes to slot 0 inside the loop
  (Ruckus's wrap, see the table) go through `CoopSetP1Y/X`, which keep `targetX/Y` in step while P1 is the target.
- **P2 in the round**: `BIT coopP2Active / BPL / JSR CoopSelectTarget` (8 B, bank B) runs per live enemy right after
  the `ENEMY_DYING`/`$0C` checks and before the type dispatch (bank-B behaviours and the bank-8
  `RemoteEnemyUpdateSubs` alike; X = enemy index, the routine keeps X and Y). `CoopNearest` picks the nearest
  targetable player by |dx| + |dy| (9-bit sum) between the enemy and slot 0 / slot `OSLOT_P2`; a tie goes to P1.
- **Targetable** = `playerState` != `PLAYER_STATE_DEAD` (3) (`ctxOther_playerState` for P2; P2 must be in the round,
  which the gate guarantees). From `PlayerHandlerDead`: state 3 covers the whole death animation and the "no lives
  left" wait (P2 stays in state 3 at 0 lives, Phase 3). The respawn is in place and instantaneous (`CODE_059A0E` sets
  state 0, then 120 i-frames). There is no separate respawn state, so i-frames do not make a player untargetable (as in
  1P, where enemies keep chasing an invincible player). Neither targetable: `coopTarget` is kept and `targetX/Y` are
  refreshed from that player.
- **Direct damage**: `CoopDamageTarget` (A = damage; keeps A/X/Y, N/Z from A) writes `playerDmgType` (P1) or
  `ctxOther_playerDmgType` (P2). P2's damage is consumed by P2's player update in the same tick's even window (P1's on
  the next tick), the deferral Phase 5 already uses.
- **Projectile ops that aim** (`ProjOp_HomingPlayer`, `ProjOp_GetPlayerDist`, `ProjOp_GetPlayerSide`, bank 9):
  `CoopProjTarget` (X = projectile index) picks the nearest targetable player to the projectile itself (the shooter
  is not recorded), returns its slot in Y (0 or 39) and its position in `targetX/Y`. Slot 0 is the resident player,
  so the rule is also right while a projectile that touched P2 runs its ops with P2 swapped in (Phase 5
  swap-on-hit, unchanged). P2 not in the round: slot 0.

### 1. Items (`CODE_078916`, bank 7, even tick, P1 resident)
Every collect test in the routine goes through one touch routine, `CODE_078BC5`. It tests the resident player (slot 0,
`playerState` != dead) against the item in slot `scratch4` (box `scratch2/scratch3`) and sets bit 7 of the item's
`objState`. The callers then apply the effect at once, to the resident's variables and to shared ones:
- the drink (`CODE_078982`, rounds 20/40/60/70/79/80): `bubbleVariant`;
- round items (`CODE_0789F7` -> `RoundItemCollectHandlers`): hearts, candy/shoe bits, lives (unreached), secret door
  (`ram_007B`/`playerDmgType` = 0), and shared effects (holy cup, clock, crystals, pencil, tree, parasol); then
  `AddScore` (via `currentPlayer`) and `CODE_078A70`;
- the big reward (`CODE_078CCE`: shared `powerUps` bits 2-5, `roundFlags`, `AddScore`);
- the end-of-round bonus rewards (`CODE_078D5C`, `AddScore`).

Running only "the collect part" in the even window would mean duplicating the routine: in every path the touch and
the effect are interleaved with the spawn/timer code. So the Phase 5 projectile pattern is used instead:
- **Tail test.** `CODE_078C23`, the miss exit of `CODE_078BC5`, now jumps to `CoopItemOther`; the hit path got its own
  `RTS`. `CoopItemOther` (co-op only) runs the same test for the other player (slot `OSLOT_P2`,
  `ctxOther_playerState`). On a touch it sets bit 7, runs `CoopShotRestore` and swaps the collector in with `CoopSwap`.
  It keeps X (`CODE_078D5C` loops with X) and leaves scratch0/1 alone (`CODE_078D2D` counts in scratch0).

  The unchanged effect code then credits the collector: its hearts, its candy/shoe bits (exchanged by `CoopSwap`),
  its `bubbleVariant`, and `AddScore` with `currentPlayer` = 1. Shared effects stay shared. Later tests in the same
  call check the new resident first, then the other player, so the rule is symmetric.
- **Swap back.** Every exit passes `CODE_078A67`, which now calls `CoopItemEnd` instead of `LDA ram_0550`. P1 is put
  back before `CODE_078EBE`, the holy-cup palette flash, because it calls `SetRoundPalette`, which reads
  `currentPlayer`. The even window and everything after it see P1 resident as before.
- **Priority.** The resident (P1) is tested first, so P1 wins a simultaneous touch.
- **Drink eligibility.** The original rule was "skip if `bubbleVariant` != 0 or `playerLives` = 0", for P1 only.
  - `CoopDrinkGate` computes eligibility per player (bit 0 P1, bit 1 P2). The drink is spawned and tested while at
    least one player may drink; in 1P this is the same test.
  - `CoopDrinkTouch` replaces the drink's `JSR CODE_078BC5` and tests only eligible players. `coopItemNoOther` blocks
    the tail test for an ineligible P2; an ineligible P1 is skipped by calling `CoopItemOtherTest` directly.
  - Without this, a P2 that had already drunk would take the drink from P1 every even tick (it respawns as soon as
    `ram_054C` is 0).
- **`Collect*` handlers.** None assumes P1 beyond the resident's variables.
  - `CollectSecretDoor` clears only the collector's `ram_007B`/`playerDmgType` (round transition, Phase 7).

### 7a.1 The 1P death flow, mapped
`PlayerHandlerDead` (bank 5, player state 3), run inside the dying player's own update:
1. First call (`objAnim` != $2A): death animation, `DEC playerLives`, `bubblesLifespanLevel` -1 (not below 0),
   `livesCurrentPos |= 3` (HUD refresh), `ram_047B` = 0, death sound.
2. Every later call: `ram_047B` counts to $24, waits there until the body has fallen below Y $E0, then $25.
3. At $25 (`CODE_0595C1`): `CODE_059A0E` (state 0, `objState` 1) and `CODE_0596B4` (per-life bytes, candy/shoe bits,
   hearts 1). Lives left: round 20 sets `wideHScroll` = 1; then `multiplayer == 1` -> `CODE_05962D` (alternating 2P:
   other player's turn, round restart through a fade), else the in-place respawn `CODE_0595E3` ((31,193), 120 i-frames).
   No lives left: nothing more; the player is in state 0 with 0 lives.
4. `RoundUpdate`'s end (resident only): state 3 -> skip the end checks; else `roundFlags & $20` (bonus game), then
   `CODE_0997C6`: lives 0 and state 0 -> game over (`CODE_058B5A`); then the bonus-prize / round-clear checks.

So "out" = lives 0 and not dying. Lives only drop at step 1, so lives 0 with state != 3 can only follow step 3.

**Does the alternating switch run in co-op today?** No: the harness (and any co-op start through the 1P menu entry)
has `multiplayer` = 0, so step 3 always takes the in-place respawn. With `multiplayer` = 1 a P2 death in its window
would have run `CODE_05962D` with P2 resident: `currentPlayer ^= 1`, bonus progress swapped, lives reloaded from the
HUD digits, and a fade into a round restart. Now `CODE_0595D7` reads `multiplayer` through `CoopMultiplayer`, which
returns 0 while `coopMode` != 0 (`multiplayer` itself is unchanged).

### 7a.2 Design: out players
- **P2 out.** `CoopP2Window` checks P2's lives right after P2's player update (P2 resident): lives 0 and state != 3
  means that P2's last death has just ended. The window swaps P1 back and calls `CoopP2Deactivate`
  (`coopP2Active` = 0, `objState+39` = 0, bubble budget 20/19), then restores `$A000` as usual. Cost: `LDA/BNE`,
  7 cycles per window. Every co-op hook is gated by `coopP2Active`, so P2's leftover context in `ctxOther` is inert:
  no window, no targeting (6a), no items, water, quake, capture, projectile or hazard tests for P2.
- **P1 out: role exchange.** Keeping an out P1 resident would have needed gates in the player update, the touch
  loop, items, collisions, the HUD, the game-over test and every slot-0 reader. Instead the partner becomes the
  resident player for good:
  - `RoundUpdate`'s end (after the `playerState == 3` skip, before the `roundFlags & $20` and game-over tests):
    `LDA playerLives / BNE` -> `CoopResidentOut`. In 1P this costs 7 cycles per tick and only calls the routine on a
    game-over tick, where it changes nothing.
  - `CoopResidentOut` with the partner in the round: `CoopShotRestore`, `CoopSwap` (partner in slot 0 and the native
    vars), then `coopResident` = 0 and `coopRoles` ^= 1. The out player goes to `ctxOther` / slot 39, which
    `CoopP2Deactivate` frees. It also sets `livesCurrentPos |= 3`, so the HUD is redrawn for the new resident.
    `RoundUpdate` then skips the rest of its end checks for this tick.
  - From then on the game is the partner's 1-player game: slot 0 = physical P2, `currentPlayer` = 1 (pad 2, P2's
    score/lives digit set, P2's palette colour at the next round start, P2's game-over colour), `coopP2Active` = 0
    (enemies target slot 0 through `CoopTargetTick`, items, camera and the HUD read the resident as in 1P).
  - `CoopSwap` / `CoopSwapCtx` set `currentPlayer = coopResident ^ coopRoles`, so `currentPlayer` always names the
    physical player whose context is native. Nothing else changes: `coopResident` is still the swap parity (0 at
    every tick end and window entry), so every Phase 3-6 rule stays valid.
  - `coopRoles` is put back when the game ends: `CoopResidentOut` without a partner (both out) exchanges the contexts
    back with `CoopSwapCtx` (new entry point: `CoopSwap` now does the object arrays first and falls into
    `CoopSwapCtx`, the scalars + powerUps + bookkeeping, same cost), so game over and continue see physical P1
    resident. `CoopNewGame` clears `coopRoles` too.
- **Game over** = both out. `CoopResidentOut` returns C = 0 when no partner is in the round, and the original test
  (`lives 0 && state 0` -> `CODE_058B5A`) follows. The game-over and continue screens are single-player screens
  (P1's colour, one dragon sprite); see the 7b list.
- **Continue** (`CODE_058DB2`, after `ResetLivesAndScore` for P1): `CoopContinue` runs `ResetLivesAndScore` again with
  P2's context swapped in (`CoopResetOther`: `CoopSwapCtx` / `ResetLivesAndScore` / `CoopSwapCtx`): 3 lives, 1 heart,
  score and extra-life accumulator 0, exactly as the original continue does for P1. The round restart then spawns
  both players (`CoopRoundStartP2`). `CoopNewGame` uses the same routine (P2's score digits were never reset at a new
  game before).
- **Round starts with one player out**: `CoopRoundStartP2` returns at once when `ctxOther_playerLives` = 0. That byte
  belongs to whichever physical player is not resident, so the rule covers both "P2 out" and "P1 out (roles
  exchanged)". The out player stays out until a continue or a new game.
- **Alternating-2P death switch.** `CODE_0595D7` reads `multiplayer` through `CoopMultiplayer`, which returns 0 when
  `coopMode` != 0. 1P and alternating 2P read `multiplayer` as before.

### 7a.4 Score attribution
Owners are physical player ids, i.e. `currentPlayer` of the player who acted. `$FF` means unknown and is credited to
`currentPlayer`, as in the original. In 1P and alternating 2P every owner is `currentPlayer`, so all credit is
unchanged (regress and the alternating comparison pass).
- `coopBubOwner[20]`: the toucher on a touch pop (`CODE_0989BD` -> `CoopTouchPop`, in `UpdateBubbles` for P1 or in
  P2's touch pass); for a chain pop in `BubblesTravelUpdate`, the owner of the popped bubble that touched it
  (`CoopChainOwner`, after `INC ram_051B`); a water-flood piece inherits the water bubble's owner (`CoopFloodCopy`).
- `coopKiller[10]` (per enemy index): set at the kill. Enemy bubble popped: the bubble's owner (`CoopCountKill`,
  replaces `INC ram_051A` in `PopBubble`). Special-bubble effect (`HazardCheckEnemies`): the effect bubble's owner
  (`CoopHazEnter` / `CoopHazKill`). Holy cup: the collector (`CoopHolyKill`). Emerging-bubble hit (`CODE_0B9AA9`):
  the shot owner, `currentPlayer ^ coopShotSwapped` (`CoopShotHit`).
- Direct kill scores: `CODE_0B8446` (effect / holy-cup kill) and `CODE_0B9B2F` (enemy removed with 500 points: popped
  enemy off screen, hit-count kills, death animations) call `CoopKillScore` / `CoopKillScoreEnd` instead of
  `AddScore`. These credit the killer via `CoopAddScoreAs`, which sets `currentPlayer` around `AddScore`. The `End`
  variant clears the record.
- Multi-kill bonus: `coopKills[2]` counts each player's enemy-bubble kills (`ram_051A` stays the combined total; it
  is also the shared item statistic `ram_0549`). At the award (`CODE_099EA5`), `CoopKillSplit` gives the other
  player's share its own award (`CoopMultiAward` = the original rule and table, including the 3+ bonus-reward flags)
  credited to him, and returns the current player's share to the unchanged original code.
- Records are reset at every despawn-all (`CODE_0FE36B` -> `CoopDespawnAll`), so nothing crosses a round or a turn.
- **Extra life**: after the resident's `CODE_099D3B`, `BIT coopP2Active / BPL / JSR CoopExtraLifeOther` runs the same
  routine for the other player. His lives are exchanged with `playerLives` and `currentPlayer` is flipped around the
  call, which indexes his accumulator (`$049A-$04A0`). After a role exchange the resident's own check covers physical
  P2.
- Not changed (resident credit): boss defeat 500 (bank 8 `$92A0`), the round-clear 1000 bonus (bank B `CODE_0B82D0`).
  Both are team events.

### Open issues
- Ownership is approximated in four places:
  - a bubble popped by something other than a touch or a chain (none was seen) is credited to `currentPlayer`;
  - simultaneous chains of both players are split by the owner of each popped bubble, not by who started the
    chain;
  - the boss-defeat 500 and the round-clear 1000 go to the resident;
  - projectile kills are not attributed (no such score path was found).
- When the resident (P1) is dying, the round-clear and bonus-game checks wait for his respawn (or role exchange),
  as in 1P, even if P2 is alive.
- If P2 enters the secret door while P1 is on his last death, the bonus game starts with P1 out and resident. The
  out check then runs on the first tick of the next round (role exchange there, after P1's walk-in). This was not
  reproduced in a run; it follows from reading the code.
- "Any player's death calms enemies and resets the hurry-up" makes co-op easier than 1P when one player dies often.
  It is a design choice, documented here.

### Regress rules (`tools/perf/perf.py`, owner approval (a); the only exclusions added)
1. HUD nametable rule: a nametable byte at dump offset `o` (either 1 KB nametable, `o & $3FF`) is ignored iff its row
   `(o & $3FF) >> 5` is 2 or 3 and its column `o & 31` is 2..29 (offsets `$042-$05D`, `$062-$07D`, `$442-$45D`,
   `$462-$47D`), both values have the same bit 7, the original value `& $7F` is in `HUD_NT_TILES` = {`$5C`, `$5D`,
   `$66-$7F`}, and the new value `& $7F` is in `HUD_NT_TILES`, or in `HUD_BONUS_GLYPHS` = `$40-$4C` only if in the
   new run's RAM of that tick or the tick before the cell's half register (`chrBankA` for bit 7 = 0, `chrBankB` for 1)
   is `$18` and the other one `$3A` (the NMI remap condition).
2. HUD icon OAM rule: an `OAMBuffer` entry (`$0200 + 4e`, 4 bytes) is ignored iff in BOTH runs it was last written by
   `DrawObjects` while it drew object slot 19 (new harness option `icon_trace`: exec hooks on `CODE_0FEF43` /
   `CODE_0FEFF5`, where scratch4 = the slot, cleared at `DrawObjects`/`DrawObjectsBody`/`CODE_0FF064`/`CODE_0FF079`/
   the full exits; every OAMBuffer write marks its entry; `<scen>.icon` per tick), its tile, attribute and X bytes
   are equal and the new Y is >= `$EF`.
Nothing else: no attribute, palette or RAM exclusion (the NMI remap keeps `chrBankA/B` original, so no CHR-id rule).
`regress --reuse-base` re-runs a base scenario whose `.icon` file is missing; base dumps are unchanged by the trace
(cmp of `base/r01.dump` before/after).

### Design
Every co-op path runs only while `coopP2Active` (both players in the round). 1P, and a game where one player is out
(role exchange or P2 out), keep the original code byte for byte in behaviour.

**Camera (8.1, 8.2).** `CODE_0788CC` (bank 7, every RoundUpdate tick of round 20, before P1's update, P1 resident) jumps
through `CoopRunB5` (COOP_CODE2: a nested `RunBankedSub`, which keeps the outer return bank on the stack) to
`CoopCamera` in bank 5:
- each player pushes by the 1P rule (`playerHeld` of his last update: LEFT, or LEFT+RIGHT, at X < 80 pushes left; RIGHT
  at X >= 176 pushes right); a dying player (state 3) does not push (`CoopCamWant`);
- opposite pushes: no scroll (the camera stalls, no jitter);
- leash: the scroll is made only if every player who does not push stays within the screen edges after it
  (`COOP_EDGE_L` 16 .. `COOP_EDGE_R` 240; `CoopCamLeash` tests X >= 18 / X <= 238);
- world ends as in 1P (`wideHScroll` 1 / 255, odd, step 2);
- the pusher holds still on screen, as P1 does in 1P (`coopCamHold` bit = `coopResident` at his update, read by
  `CoopMoveX`); the other player moves with the world by exactly 2 px in the same tick (his world X stays constant).
**Screen edges.** `CODE_0594EB` (bank 5, X step of every player update) -> `CoopMoveX`: in round 20 a step that would end
past 16 / 240 is not taken (moving away from an edge always is). With the leash this keeps both players on screen; two
players pulling apart end up at the two edges (max separation 224 px) with the camera still.
**Shifter (8.3).** `CODE_0FFD89` (even tick) skips slot `OSLOT_P2` entirely while P2 is in the round (no shift, no cull):
the camera moves P2. The Phase 3 cull-only exemption is removed. (P1's slot 0 was never in its list.)
**Ruckus wrap (Phase 8 list).** `CODE_08882A` -> `CoopRuckusWrap` (bank F) for both players (slot 0, then 39):
- top clamp Y < 8 -> 8 (P2 used to rise above the top, Y 249-255, invisible);
- fall through the floor (Y >= $E8): the 1P exit is Y 0, X $A0, camera $FF. In co-op the camera moves right by
  min($FF - camera, partner X - 16), even, so the partner stays on screen (he moves with the world); the faller lands

### Design
One KB holds the 16 bubble tiles plus exactly 4 frames (one per block position, 4 x 12 tiles). A frame drawn from
another block position only needs its OAM tile numbers shifted by the block difference (`$06`, `$20`, `$26`, ...).
Every pair of frames must share some KB: with 4 frames per KB that is a covering design, at least v(v-1)/12 KBs for v
frames (196 for 49), but CHR ROM is at the MMC3 maximum (256 KB) with 126 free ids. The projective space PG(3,3) has 40
points and 130 lines of 4 points with every two points on exactly one line; 4 disjoint lines are the original banks
`$40-$43` (their 16 frames at home), the other **126 lines are new banks: ids `$80-$97`, `$9A-$FF`** (all free ids).
The 40 points are the 16 frames of `$40-$43` plus the 24 other frames seen in the runs (all 39 seen frames + 47C as
40D). The 10 frames never seen are mapped to the nearest frame of the same block (pixel distance): 44B 45B 4BB -> 47B,
4BA 4CA -> 40A, 4DA -> 44A, 4EA 4FA -> 47A, 4EB -> 4DB, 4EC -> 45C. The point labelling and the position of each frame
in its banks were optimised (hill climbing, weighted by the measured pair counts) so that most players stay at their
home block: in the measured pairs 21 % of player-ticks need a shift.

Generator: `tmp/coop_scripts/p91/mkpairchr.py` (`--check` verifies both outputs; reads banks `$40-$4F` from a build's
CHR, identical to the original ROM) -> `src/chr/CoopPairs.chr` (126 KB, banks in id order) and
`src/coop/coop_pairtab.inc` (CoopFrmIdx 64 B: bank/block -> point; CoopPtBank/CoopPtPos 40+40; CoopTriLo/Hi 40+40;
CoopPairBank/CoopPairPos 780+780, triangular by point pair). `statcheck.py`: all 1560 ordered pairs give a bank with
both frames' bytes at the chosen positions and the bubbles intact.

Runtime, every DrawObjects call while `coopP2Active` (`CoopDrawObjects`, bank E: `BIT coopP2Active / BPL / JMP
CoopDrawPair`, 8 B, the last free bytes of COOP_CODE), `CoopDrawPair` in COOP_WRAM_CODE:
1. both players drawn (`objState` != 0; the blink hides are already applied) and `objChrBank` different;
2. memo: if the 7 inputs (both `objChrBank`, `objImgOfs`, `objImgOfsHI`, and `sprPrgBank`) equal the last call's, the
   last result is reused (46 % of the calls in c01);
3. else both banks `$40-$4F` -> `CoopFramePt` (bank, image -> point; image block from `objImgOfs`), pair lookup ->
   bank and the two positions; `CoopPairShift` for a player not at home: copies his image (`$A000` table entry of
   `sprPrgBank`, Rule 9 order switch as DrawObjectsBody does next) into `coopImgBuf` with the tile numbers shifted,
   cached per player (copy redone 137 times in 3000 ticks of c01), and points `objImgOfs/HI` at `coopImgEnt` (the
   table read `$A0xx + objImgOfs` wraps to the WRAM data area);
4. `CoopDrawObjects1P` (icon hide + DrawObjectsBody), then `chrBankC` = the pair bank (bubbles need nothing: their
   tiles are in every player KB), `objImgOfs/HI` put back.
A player in slot 0 with a bank outside `$40-$4F` (found: anim `$A5` = `anInvaderDie`, bank `$5B`, while stuck in
state `$0C`, rounds 4, 13, 18, 73 of the charge runs) is drawn from a slot 1-3 that already holds that bank, else
from a slot no other drawn object uses (lent for this call: DrawObjects writes `chrBankD-F`, `CoopForRestore` puts the
old value back at the next call or in `CoopP2Deactivate`), else without a bank write (`objChrBank` 0 for the call), so
that the other player is always right and only the stuck player shows the other KB (as before the fix).

### A. Round-50 missile tractor
The tractor is round 50's per-tick routine `CODE_078462` (installed in `ram_005B` by `CODE_078404`, run by `CODE_078247`
from `RoundUpdate` before P1's update, so P1 is resident: slot 0 = P1, `OSLOT_P2` = P2). Its whole path, checked for
player reads:

| routine | what | player read |
|---|---|---|
| `CODE_078462` | state (`openingCounter` 0-6) timer `openingCycle`, speed `DATA_0784E3` added to `wideHScroll` (the tractor's position, an IRQ split), bounce at the ends | none |
| `CODE_0784EA` | state 6 with `openingCycle` 0: `SpawnProj psMissileTractor` at the tractor's X | none (X from `wideHScroll`) |
| `AnimateMissileTractor` | BG CHR animation (`bgAnimValue`) | none |
| `CODE_078549` | the reaction, see below | **`objX` / `objY` of slot 0** (the only one) |
| `psMissileTractor` -> `ProjOp_TractorMissile` -> 3 x `psGravityProj` | missiles spawn at the parent's X, fly up | spawn: none; contact `PO_GET_PLAYER_CONTACT` / `PO_HURT_PLAYER` = Phase 5 (`CoopProjCheckP2`), both players |

`CODE_078549` (scratch3 = tractor X = `$80 - wideHScroll`):
- states 0-2, 5, 6: reads the player once. On the floor (Y = `$C4`): state 1 (moving left) with the player at or left of the
  tractor, or state 2 (moving right) with the player right of it -> state +2 (fast, toward the player), sound
  `snMissileTractor`, `openingCycle` `$20`. Else, high (Y < `$60`) within `$30` px -> state 6, `openingCycle` 1 (stop and
  fire: the missile leaves one tick after the player is out of that zone, original behaviour).
- fast states 3/4: no player read; the same "high" test runs on the tractor's own position (scratch0/1 left by
  `CODE_078462`), which fires missiles at fixed positions.

**Rule (co-op, both players in the round): the first player who triggers it, P1 first.** `CODE_078549` starts with
`BIT coopP2Active / BMI` -> `JMP CoopTractor` (PRG-RAM). `CoopTractor` runs the original code for P1
(`JSR CODE_078549_1p`); if `openingCounter` is unchanged (P1 triggered nothing) and the state is not 3/4, it runs the same
test with P2's position (`objX/objY+OSLOT_P2` -> scratch1 / A, `JMP CODE_078549_pos`, the original `STA scratch0`; scratch3
is still set). A P1 re-trigger of state 6 (6 -> 6, only the timer changes) also runs P2's test; in state 6 P2 can only
re-trigger the same way, so the result equals "P1 first". "Nearest player" was not used: the two tests are per player
and side-dependent (floor) or zone-based (high), so "whoever satisfies it" is the natural co-op version and keeps P1's
result whenever P1 triggers. 1P, and a game with one player out (`coopP2Active` = 0), run the original code (the
playing player is resident in slot 0).

### B. Sprite overflow with two players
**Measurement (`p93/flick.py`).** Per rendered frame of co-op play: the expected sprites of each player (image struct at
DrawObjects / `CoopDrawPair` entry, as `pairchk.py`), latched by the OAM DMA and kept on lag frames (`NMIShort` does no
DMA: the PPU shows the last tick's OAM again); at frame end the PPU OAM is evaluated per scanline (first 8 entries in
OAM order are drawn, 8x16: lines Y+1..Y+16). Per player and frame: ok / part (>= 50 % of his sprite lines) / big
(< 50 %) / inv (0 lines, incl. sprites cut off a full buffer) / hid (not drawn: blink) / off. Runs = consecutive big|inv
frames. An exact overlap (both players the same frame at the same place) counts as one image. Scenarios c01 c05 c17 c20
c22 c50 c64 and the floor style f17 / f64 (both pads walk and tap B, never jump: both players on the bottom row; inputs
per tick, independent of lag).

Before (`p92g`) and after (`p93b`), co-op play frames (`final_flick_p92g.txt`, `final_flick_p93b.txt`); "big+inv" = frames
with less than half of the player's sprite lines shown, "inv" = none shown; "runs of 2" = two such frames in a row;
"others" = share of dropped sprite lines of all other objects:

| scen | frames (lag) | P1 big+inv / inv | P2 big+inv / inv | P1 runs of 2 | P2 runs of 2 | longest run | after: players big+inv | others dropped before -> after |
|---|---|---|---|---|---|---|---|---|
| c01 | 2153 (122) | 95 / 0 | 69 / 0 | 0 | 9 | 2 | 0 | 9.9 % -> 13.8 % |
| c05 | 2215 (180) | 117 / 0 | 143 / 0 | 13 | 23 | 2 | 0 | 10.8 % -> 14.0 % |
| c17 | 2768 (717) | 331 / 17 | 490 / 46 | 28 | 221 | 2 | 0 | 21.1 % -> 27.2 % |
| c20 | 2130 (3) | 36 / 10 | 62 / 10 | 0 | 2 | 2 | 0 | 4.1 % -> 8.1 % |
| c22 | 2167 (148) | 344 / 32 | 418 / 37 | 0 | 55 | 2 | 0 | 19.0 % -> 25.5 % |

Before, totals: frames with sprites over the limit P1 5345 / P2 7122 of 23685; cut off a full buffer (c64, f64) 392 frames
each; fully invisible (inv) frames P1 80 / P2 119, of which runs of 2 frames P1 9 / P2 38; no run longer than 2. Every
bad frame is on the player's losing parity (P1 odd ticks, P2 even ticks), and every run of 2 is a lag frame (bad frames
on lag frames: P1 384, P2 990). After: 0 frames with any player line dropped or cut; other objects' dropped lines
16.0 % -> 19.9 %, their fully dropped entries 39478 -> 54612 (c50 differs in play: the tractor, item A).
Cross-check `pairchk`: the "partial" frames of p92g (91 per player, c64 OAM full) are gone (0).

**Cause.** `DrawObjectsBody` alternates the slot order (even ticks 0..39, odd 39..0), so every tick one player is first in
OAM and the other last: P1 loses lines only on odd ticks, P2 only on even ticks (no bad frame on the other parity). The
2-frame runs are all lag frames: the losing tick's OAM is shown twice. No per-tick rotation can prevent that (whether
the next frame lags is not known when the OAM is built), and re-ordering at the lag NMI would need an OAM DMA there
(the buffer can be half rebuilt by the next tick's DrawObjects) or an OAMADDR rotation (2C02 OAM corruption with a
non-zero OAMADDR at render start).

**Change: both players first.** `CoopDrawPair` (every co-op draw, all its paths) draws through `CoopDrawObjectsC` (the
icon hide of `CoopDrawObjects1P`) -> `CoopDrawBodyC`: the player the body would draw last is drawn first by
`CoopDrawSlot` (one step of the body's slot loop, same OAM bytes, at OAM 0, after `CoopDrawMap` = the body's own bank map
in Rule 9 order and `oamBufferPos` = 0), hidden for the body's scan, which is entered at `DrawObjects_EvenScan` (Y = 0) /
`DrawObjects_OddScan` (Y = 39). Order: even P2, P1, 1..38; odd P1, P2, 38..1 (the other objects keep the original
alternation; the two players still alternate between themselves). The pre-drawn player's chrBank write is made after the
body, where the original order made it (last). Slot 39's objState hide/restore is in bank E (`CoopP2ObjHide/Show`,
COOP_CODE2: the Phase 6 checker accepts slot-39 objState writes only from bank-E co-op code); slot 0 is hidden in place.
Original order when `ram_0475` != 0 (pause, announcements) or when the player who would be last is not drawn (blink).
Two players use at most 6 sprites per line (3-wide frames), so they can no longer lose a line or be cut off a full buffer.
Visible side effects: the other objects on the players' lines lose more (numbers above), and a player overlapping another
object is now always in front of it (before: in front every other tick).

## Test pipeline speed-up
The full verification of Phase 9.3 (`tmp/coop_scripts/p93/verify_all.sh p93b`) took 83 minutes, ran one step after
the other, showed no progress inside a step and could not tell a slow run from a hung one. Owner-approved: changes to
`tools/perf` for speed and progress/status only; nothing that is checked changed. Game sources untouched.

### How to run
- Full (the checks of `p93/verify_all.sh`, parametrised; Phase 9.3 values shown):
  `python tools/perf/verify.py full p93b --prev p92g --alt p93a --p90ref tmp/coop_scripts/p92/final_p90verify.txt`
  (`p93bf` / `p93bt` must exist; `--alt` and `--p90ref` are optional; `--base` defaults to `base`). Results:
  `tmp/verify/p93b_full/final_*.txt` (the file names of `verify_all.sh`), `summary.txt` (PASS / FAIL / INFO per step
  with its file), `run.log` (the console lines). Exit code 0 only if every step with a verdict passed (9.3's expected
  `ramidentity` FAIL at c50 therefore gives exit code 1).
- Quick (development, ~5.5 min cold): `python tools/perf/verify.py quick p93b` - 1P regress (12 scenarios), p90verify
  on c01 c17 c50 c64 w20n bn2, hudcheck c01,c20,c50, pairchk c01 c50, menutest.
- Status (from another shell): `python tools/perf/verify.py status` - running / finished / STALE, steps with elapsed
  time and run i/M, the Mesen runs alive (pid, elapsed, expected, hang limit), ETA.
- `--jobs N` Mesen processes at once (default 4), `--no-cache`, `--force` (start although Mesen.exe processes exist).

### Where the time went (measured, `tmp/coop_scripts/speed/`)
- Emulation itself: 3300 frames take 14 s in Mesen's test runner (a Lua script turns the debugger on); every 3000-tick
  run costs at least that. Harness Lua ~5 s per run, the per-tick dump ~2.5 s.
- p90verify-type runs (p90verify and hudcheck's r2 / p8 sets, 55 of ~200 runs, over half the CPU): c01 took 95 s.
  `emu.getState()` costs ~200 us per call (Mesen serializes the whole emulator, 323 keys); 211k calls = 42 s. Every
  registered exec callback is tested by Mesen on every executed instruction; one on a PRG-ROM offset costs ~0.27 s per
  3300 frames (4x one on a CPU address); p90verify registers ~110 of them: ~30 s.
- Duplicated emulation: hudcheck's r2 / p8 sets (23 runs) are p90verify's runs of the same scenarios plus the HUD Lua.
  Base / p92g runs (pixcmp, flick, tractor) were redone each pipeline; pixcmp ran the new build twice.
- Parallelism: the old steps used 1-4 Mesen processes and many steps were serial (swapcheck, tractor's 8 calls, the
  two pixcmp calls). Scaling on this 4-core machine (c01 dump run): 1 run 21.5 s, 2: 23.0, 3: 26.0, 4: 31.3, 5: 38.0
  -> 4 at once is the best (5 adds 2 % and leaves nothing for the Python side); ~170 MB per Mesen.
- Python: `perf.py regress` compared every byte of every differing tick record (4128 bytes x 3000 ticks x 12).

### Changes
- `tools/perf/harness.lua`, "Speed layer" (runs before any registration, also for the add-on Lua of the co-op
  checkers): (1) `emu.getState()` returns the table of the previous call while Mesen is still delivering the same
  memory access / exec / event (same callback type, memory type and address and a higher registration number; events
  and `emu.write*` drop it); (2) with `CFG.prg_link` (perf.py passes it) every single-address exec callback, on a CPU
  address or on a PRG-ROM offset (registered at the CPU address its ROM segment is linked at), goes into one Mesen
  callback per CPU address that calls the entries in registration order; a PRG-ROM entry only if
  `emu.convertAddress` maps the executed address to its offset. Verified in Mesen: callbacks fire in registration
  order across memory types, a PRG-ROM exec callback gets the same arguments (CPU address, opcode), a returned value
  is passed on, an error does not stop the others, `emu.stop` does not raise; the layer does the same. Dump records
  are read 4 bytes at a time (`emu.read32`), same bytes. p90verify c01: 95 -> 60 s; perf dump runs 22 -> 20.4 s;
  perf runs r01 / c01 (csv, dump, icon, prof, wprof) byte-identical before / after.
- `tools/perf/perf.py`: `CFG.prg_link`, `--timeout=1800` for Mesen (its own ~100 s script limit could cut a run when 4
  share the CPUs), `diff_offsets` (chunk-wise, same list) in `compare_runs`, `PERF_JOBS`.
- `tools/perf/verify.py` (new): the runner. A lock (`tmp/verify/verify.lock`, pid + process creation time; a second
  pipeline is refused, a lock of a dead process is replaced) and a refusal while any Mesen.exe runs. The runner joins a
  Windows Job Object (kill on close), so killing it kills every child; Ctrl-C / errors kill the children explicitly
  (taskkill /T). The step scripts run unchanged under `verify.py _step`, whose `subprocess.run` hands every Mesen run to
  the runner: at most 4 at once, longest expected first, a per-run hang limit (3x the expected time, at least +300 s;
  a hang is killed and reported, the caller gets `TimeoutExpired`), a run cache (`tmp/verify/cache`, key = hash of
  Mesen.exe / MesenCore.dll / settings.json, the ROM bytes, the Lua with its `[[path]]` strings normalized and the
  arguments; the files the Lua writes are recorded by a one-line prologue, so line numbers do not move; only exit code
  0 runs; scripts with math.random / os.time / os.clock are never cached; LRU at 6 GB). Steps run in parallel as their
  data allow (stats after the runs they read, ramdiff after both dump sets, the second pixcmp after the first, ...).
  Progress: `tmp/verify/progress.json`, console lines for step start / end and every run, a heartbeat every 30 s,
